# Схема для создания базы с нуля

Миграции объединены по таблицам. Это новый исходный набор, а не обновление старой базы: старые данные и историю миграций переносит владелец проекта. Не запускайте этот набор поверх прежней схемы. На пустой базе используется `php yii migrate`.

Каждый файл создаёт одну таблицу, порядок учитывает внешние ключи. `safeDown()` удаляет внешние ключи и таблицу в обратном порядке. Таблица `user_course` больше не создаётся.

## Платежи и купоны

| Таблица | Поля |
| --- | --- |
| `tariff` | `id`, `name`, `price`, `duration_days`, `course_limit` |
| `discount` | `id`, `code`, `value`, `status` |
| `user_payment` | `id`, `user_id`, `tariff_id`, `discount_id`, `payment_amount`, `payed_at` |
| `user_subscription` | `id`, `payment_id`, `course_id`, `start_at`, `status` |

- `price` и `payment_amount`: `DECIMAL(12,2)`, неотрицательная сумма в денежных единицах проекта, не в копейках. `payment_amount` хранит фактическую сумму оплаты, в том числе после скидки.
- `discount.value`: процент `DECIMAL(5,2)`, больше 0 и не больше 100. Код обязателен и уникален. Статус — `new` по умолчанию либо `used`.
- `user_payment.discount_id` может быть `NULL`: оплата без скидки. Уникальный индекс позволяет связать конкретную скидку только с одним платежом; платежей без скидки может быть несколько.
- `user_subscription` — одна строка на купон. Владелец и тариф определяются через `payment_id → user_payment`.
- Новый купон: статус `new`, `course_id = NULL`, `start_at = NULL`. Для `active` и `expired` курс и дата обязательны. Индексы поддерживают выборку купонов платежа, доступа к курсу и проверку срока.
- Несколько купонов могут ссылаться на один платёж. Нет уникальности по `payment_id` или по курсу, чтобы не препятствовать нескольким купонам и будущим продлениям.

Миграции готовят только схему. Обработчик подтверждённой оплаты должен в одной транзакции записать платёж, погасить скидку и создать `tariff.course_limit` новых купонов. Активация назначает курс, записывает текущее время в `start_at`, переводит купон в `active`. Проверка доступа сравнивает прошедшее время с `duration_days` тарифа и при превышении переводит купон в `expired`, возвращая уведомление. Эти операции и уведомление здесь не реализованы, согласно текущему объёму задачи.

В этой схеме длительность берётся из связанного тарифа: отдельного снимка `duration_days` в платеже или купоне нет. Поэтому последующее изменение длительности тарифа повлияет на расчёт срока ранее выданных купонов, если будущая бизнес-логика не установит иное правило.

## Курсы и шаблонные таблицы

`course.alias` добавлен непосредственно в миграцию курса: обязательное уникальное значение до 32 символов, строчные латинские буквы, цифры и `_`, первая позиция — буква. Значение `sample` зарезервировано.

Пять таблиц создаются сразу с итоговыми именами:

- `course_sample_category`
- `course_sample_topic`
- `course_sample_question`
- `course_sample_question_topic`
- `course_sample_answer_option`

Внешние ключи остальных таблиц направлены на эти имена. Создание отдельных наборов таблиц для каждого курса пока не реализовано. Поле `user.email` также включено в основную миграцию пользователя; отдельных миграций добавления email, alias и переименования больше нет.

## Проверки и существующий API

`php tests/learning-schema.php` создаёт отдельную временную MySQL-базу, применяет весь набор, проверяет связи, ограничения, состояния купонов и откат, затем удаляет тестовую базу.

Существующие `SubscriptionController`, таблица подписок в NLUser и тесты старого API подписок пока используют прежнюю структуру. Их нужно адаптировать отдельной задачей перед использованием новой схемы приложением. В рамках текущей задачи изменены только схема, миграции и относящиеся к ним проверки.

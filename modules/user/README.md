# Пользовательский API

## Вопросы, прохождение и оценки

Вопрос состоит из паттерна `{{имя}}`, JSON `pattern_values` с обязательными значениями всех вставок и типа ответа. [Схема и правила начисления](../../migrations/README.md) описывают новые таблицы.

`POST /user/active-tests/start` временно возвращает HTTP 503 с сообщением о недоступности подбора вопросов. Старая логика выбора тем, квот, рейтингов и частоты удалена; новый алгоритм пока не реализован.

Для сформированной попытки сохранены `resume`, `answer`, `timeout`, `finish`, `cancel`. Запросы требуют Bearer-токен, целочисленные `course_id` и `attempt_id`; ответ/таймаут также требуют ID текущего вопроса попытки `question_id`. При ответе передаётся `answer` либо `skip: true`. Доступ к курсу и владелец теста проверяются сервером.

Ответ содержит `id`, `status`, `question`; для активной попытки — `total`, `answered`. Вопрос содержит `id`, собранный `text`, вычисленную обработчиком `category`, `answer_type_code`, показанные `options`, `max_selections`, `remaining_seconds: 60`. Правильные ответы не выдаются. Таймер контролируется интерфейсом.

При показе сохраняются варианты и их порядок; при ответе проверяются формат и принадлежность показанным вариантам. Только `finish` проверяет правильность и начисляет баллы всем связанным единицам знаний во всех системах. Баллы ошибок хранятся положительной величиной; итог — сумма успехов и ошибок. Снимок, оценки, очистка временных данных и статус завершения сохраняются одной транзакцией.

`GET /user/tests/history?page=1` возвращает собственные завершённые тесты по 7 записей, от свежих к старым. `GET /user/tests/history/{courseId}/{id}` возвращает снимок с текстами, показанными вариантами, ответами, `answer_type`, `answer_type_code` и `is_correct`. История доступна после окончания подписки. Расчёт результата по выбранной системе пока отключён: `statistics_available: false`, `result`, `positive_score` и `negative_score` равны NULL.

Модуль user находится во внешнем Yii-проекте. CRUD вопросов, паттернов и справочников ещё не реализован; существующие ресурсные заглушки возвращают HTTP 501.

## Авторизация

- POST /user/auth/login — вход по username или email и password; доступен без токена.
- GET /user/auth/me — id и username текущего пользователя.
- POST /user/auth/logout — отзыв токена, ответ {"success":true}.

Вход принимает JSON, например {"username":"login","password":"password"} или {"email":"user@example.com","password":"password"}.
Ответ содержит auth_key, token_type: Bearer и user (id, username). В базе сохраняется только SHA-256 хеш токена.
Новый вход заменяет прежний токен. Автоматического срока истечения пока нет. За пределами локальной разработки используйте HTTPS.
400 — неверный формат данных, 401 — неверные реквизиты или токен. Cookies и CSRF-токен для входа не требуются.
Проверки авторизации на SQLite в памяти: php tests/user-auth.php.

Защищенные маршруты уже проверяют Authorization: Bearer <auth_key> через существующую модель User.
Без действующего токена — 401. Хранилище учетных записей и auth_key общее с admin API:
вход через любой модуль заменяет прежний токен этой учетной записи. Cookies не заменяют Bearer-токен.
Операции прохождения проверяют владельца теста и действующий доступ к курсу.

## CRUD-маршруты

Для каждого ресурса доступны:
GET /user/{resource} — список;
GET /user/{resource}/{id} — одна запись;
POST /user/{resource} — создание;
PUT или PATCH /user/{resource}/{id} — редактирование;
DELETE /user/{resource}/{id} — удаление.

Ресурсы: courses, categories, tests, active-tests, topics, questions, question-answer-types.

Списки по родителю:
- GET /user/courses/{course_id}/categories
- GET /user/categories/{category_id}/topics
- GET /user/topics/{topic_id}/questions

На общих списках categories, topics и questions планируются соответственно query-параметры course_id, category_id и topic_id.
tests использует владельца из токена; active-tests предоставляет операции прохождения текущего пользователя, описанные ниже.

OPTIONS поддерживается для CORS. Разрешенные источники задаются в modules.user.corsOrigins.
Маршруты требуют настройки веб-сервера на web/index.php. Прямые Yii-маршруты user/course/index и аналогичные также доступны.

Проверка маршрутов без базы: php tests/user-api-routes.php.

## Пользовательские тесты

### Обработчики типов ответов

`question_answer_type.code` выбирает обработчик из `services/question/QuestionHandlerRegistry`. `QuestionAnswerType` проверяет обязательность, регистрацию и уникальность кода.

- `choice_4_single`: один правильный вариант и три случайных неправильных из банка, затем перемешивание. Выбирается один ответ.
- `choice_multiple`: все варианты банка в случайном порядке. Правильность — точное совпадение множества с одним из допустимых ответов.
- `input_text`: варианты не выдаются, сравнение без учёта регистра и внешних пробелов.
- `ordering`: все варианты перемешиваются; проверяется одна из допустимых полных последовательностей.

Форматы JSON: `{"choice":[1,2]}`, `{"input":"текст"}`, `{"order":[2,1]}`. Варианты определяются их ID. Категория интерфейса вычисляется обработчиком, в таблице типов ответа её нет.

`resume` пропускает уже показанный вопрос, оставляя ответ NULL, и выдаёт следующий. Таймаут и «Не знаю» также сохраняют NULL. Запоздалый ответ не меняет предыдущий вопрос и не пропускает текущий. После последнего вопроса возвращается `question: null`; можно завершить попытку. Значения показанных вариантов сохраняются в истории, даже если банк был отредактирован.

Проверки: `php tests/question-handlers.php`, `php tests/active-test-handlers.php`, `php tests/question-answer-type.php`, `php tests/knowledge-schema.php`.

- `GET /user/tests` — тесты владельца токена из зарегистрированных баз курсов: `items` с `id`, `course_id`, `name`, `question_count`, `materials` (курс: `course_id`, `course_name`, список названий `categories`). Идентификатор теста локален для базы; полная идентичность — пара `course_id` и `id`. Категории читаются из `category` той же базы. Каталог и проверка подписки остаются в основной БД.
- `GET /user/tests/materials` — дерево активированных курсов действующей подписки и их категорий: `items`, у курса `id`, `name`, `categories` с `id`, `name`.
- `POST /user/tests` — JSON `{"name":"Мой тест","question_count":10,"materials":[{"course_id":1,"category_id":2}]}`. Создаёт тест и связи одной транзакцией в базе выбранного курса, возвращает 201 с `id`, `course_id`, `name`, `question_count`. Все категории должны принадлежать одному курсу; смешанный выбор возвращает 400. Пользователь берётся из токена; название обязательно (до 255 символов), question_count — обязательное целое число от 1 до 30, нужна хотя бы одна доступная категория. Повторные категории объединяются. Доступ проверяется заново при сохранении.

Категории читаются из базы курса по проверенному alias. API передаёт `course_id` вместе с локальным ID категории; в `test_category` находятся только `test_id` и `category_id`. Создание конфигураций тестов и их просмотр доступны, запуск пока отключён.

Итоговая структура связи включена в миграцию создания `m260913_000008_create_test_category_table`; актуализацию существующей базы выполняет владелец проекта. Проверка без рабочей БД: `php tests/user-tests.php` (SQLite в памяти).

## API подписки и платежей

Все операции требуют Bearer-токен, пользователь определяется только из него.

- `GET /user/subscription` — `subscription` (тариф, начало и конец, либо `null`) и `slots` (`total`, `used`, `available`). `/user/subscriptions` — алиас этой сводки.
- `GET /user/tariffs` — персональные предложения: `items` с `id`, `name`, `price`, `duration_days`, `course_limit`, `is_switch`, `remaining_value`, `credit_amount`, `payment_amount`. Цена `price` — полная стоимость тарифа, `payment_amount` — сумма к оплате с учётом остатка текущей подписки.
- `GET /user/payments?page=1` — история платежей: `items` и `pagination`, по 10 строк, `payed_at DESC, id DESC`. Поля строки: `id`, `tariff_name`, `course_limit`, `duration_days`, `payed_at`, `payment_amount`, `discount_type`, `discount_value`. Суммы — десятичные строки; тип скидки — `percent` / `amount`. Данные тарифа и скидки читаются из связанных таблиц; сумма берётся из самого платежа.
- `POST /user/payments` — тестовая оплата, JSON: `{"tariff_id":1,"expected_amount":"700.00","discount_code":"OPTIONAL"}`. Ответ: `payment_id` и сводка подписки. Цена и скидка рассчитываются сервером. Необязательный `expected_amount` — показанная пользователю сумма, а не источник цены. При несовпадении с новым расчётом сервер возвращает 409 без записи платежа. Платёжный провайдер и защита от повторной обработки пока не подключены. Каждый успешный запрос записывает отдельный платёж.
- `POST /user/courses/{id}/activate` — занять слот текущей подписки. Ответ: `slot_id`, `expires_at` (дата окончания связанной подписки, в слоте не хранится). Повтор для активного курса не расходует второй слот.

Каждая оплата обновляет одну и ту же подписку пользователя: тариф, лимит, начало и конец срока. Подписка не ссылается на платёж; история платежей ведётся отдельно. Если новый лимит меньше числа активных курсов, лишние слоты деактивируются начиная с последних активаций (`activated_at DESC, id DESC`). Дата активации сохраняется, дата отключения записывается в `deactivated_at`. Увеличение лимита не восстанавливает отключённые курсы: нужна явная активация, создающая новую запись слота.

Отсутствие действующей подписки или свободных слотов при активации даёт 409, неверный промокод — 400, неизвестный тариф/курс — 404. По истечении срока подписки доступ исчезает автоматически. При последующей оплате старые слоты закрываются, не включаясь заново. До первой оплаты сводка пуста.

Проверка бизнес-сценариев, аутентификации и владельца без рабочей БД: `php tests/user-subscriptions.php`.

Для Apache с CGI/FastCGI в `web/.htaccess` включён `CGIPassAuth On`: он передаёт заголовок Authorization в PHP. Без него вход по паролю работает, но `/user/auth/me` и `/user/auth/logout` получают запрос без токена и возвращают 401.

Проверка через работающий Open Server: `php tests/user-auth-http.php --local-apache`. Она использует `http://nl.local` и БД из `config/db/db.php`, создаёт временную учётную запись и удаляет её в `finally`. Проверяются CORS, вход, три независимых восстановления сессии, выход, удаление токена в БД и отказ для отозванного токена. Существующие учётные записи не изменяются.

## Перерасчёт при смене тарифа

Остаточная стоимость = цена текущего тарифа × оставшиеся дни / полный срок подписки. Дни считаются как 24-часовые интервалы, неполный оставшийся день округляется вверх; результат округляется до копеек. Источники срока — `starts_at` и `expires_at`. Если остаток строго больше 100 ₽, он вычитается из стоимости нового тарифа. Итог не ниже нуля. При остатке ровно 100 ₽ или меньше зачёта нет. Истёкшая/будущая подписка не даёт зачёт; повторная оплата того же тарифа также не является переходом.

При промокоде сначала рассчитывается скидка от полной цены нового тарифа, затем вычитается остаток подписки. В `payment_amount` записывается итог, включая ноль при бесплатном переходе. Лимиты и деактивация последних курсов работают как при обычной оплате. Расчёт выполняется заново внутри транзакции оплаты.
# Профиль аккаунта

## Дашборд

`GET /user/dashboard` сохраняет список доступных курсов, подписку, последние тесты и количество завершений. `stats_30_days.tests_completed` учитывает последние 30 дней по UTC включительно, без будущих и недатированных записей. `stats.tests_completed` учитывает всю собственную историю.

Старые рейтинги и рекомендации удалены. До реализации новой статистики возвращается `statistics_available: false`; `answer_result`, результат курса, рейтинг темы, `topics_practiced` и `continue` равны NULL, `has_rating` — false. Списки `review_topics` и `study_recommendations` пусты. Недоступная оценка не заменяется нулём или 50%.

`GET /user/dashboard/chart` временно возвращает HTTP 503 с понятным сообщением. Переключение системы оценки, графики и рекомендации по `required` будут реализованы отдельно. Проверки: `php tests/dashboard.php`, `php tests/course-program.php`.

`GET /user/profile` возвращает профиль текущего пользователя:
`{"first_name":"","last_name":"","photo_url":null}`. До первого сохранения запись не создаётся.

`POST /user/profile` принимает `first_name`, `last_name` (строки до 100 символов)
и необязательное поле `photo` через `multipart/form-data`. Без фото можно отправить JSON.
Отсутствующие поля сохраняют прежнее значение. Ответ содержит сохранённый профиль.
Для обоих запросов нужен `Authorization: Bearer <auth_key>`; пользователь определяется по токену.

Фото: JPG, PNG или WebP, до 5 МБ и 4096 × 4096 пикселей. Файлы хранятся
в `web/uploads/avatars`, каталог должен быть доступен для записи веб-серверу.
В таблице `profile` хранится относительный путь. Новое фото заменяет прежнее.
Миграция `m261003_000001_create_profile_table` находится в `migrations/main`:
`id`, уникальный `user_id`, `first_name`, `last_name`, `photo`; полей дат нет.
Применение к рабочей базе выполняется владельцем через `php yii migrate`.
Проверка: `php tests/profile-api.php` (отдельная временная MySQL-база).

# Пользовательский API

## Прохождение тестов

`POST /user/active-tests/{action}` требует Bearer-токен. В каждом запросе передаётся целочисленный `course_id`:

- `start`: `test_id`. Создаёт полный набор вопросов, при повторном запросе возвращает существующую активную попытку.
- `resume`: `attempt_id`, `question_id` текущего вопроса попытки из списка тестов. Первый непройденный вопрос записывается как пропущенный, показывается следующий. Если все вопросы уже отвечены, `question_id` не нужен.
- `answer`: `attempt_id`, `question_id`, `answer` (`{"choice":[1,2]}`, `{"input":"текст"}` или `{"order":[2,1]}`). Для «Не знаю» — `skip: true` без `answer`.
- `timeout`: `attempt_id`, `question_id`. Интерфейс вызывает действие по истечении 60 секунд: вопрос записывается как пропущенный, показывается следующий. Время открытия в БД не хранится, сервер не проверяет длительность.
- `finish` / `cancel`: `attempt_id`.

Ответ содержит `id`, `status`, `question`; для активной попытки также `total`, `answered`. Текущий вопрос: `id` записи `active_test_question`, `text`, `category`, `options` (`id`, `text`), `remaining_seconds`. Правильный ответ клиенту не передаётся. `question: null` у активной попытки означает экран завершения. Список `/user/tests` возвращает `active_attempt_id` и `current_question_id`, оба nullable.

Темы берутся из категорий теста. Давность определяется по трём последним завершённым тестам пользователя во всём курсе (по убыванию `completed_test.id`): 0, 1, 2 балла; более старые и новые темы — 3. Отменённые попытки не учитываются. Рейтинг использует последние 10 записей `user_topic_stat` по убыванию `id`: сумма положительных / сумма модулей всех баллов. При отсутствии ненулевых баллов — 50%. Диапазоны 40–60% включительно дают 3 балла; 20–40% и 60–80% без центральных границ — 2; остальные — 1. Приоритеты суммируются, равенство разрешается случайно.

Для первых трёх тем квоты: `ceil(Q/2)`, остаток, `floor(Q/6)`, где Q — 1..30. Нулевые квоты не требуют темы. Если выбранные темы не позволяют набрать уникальные вопросы, попытка не создаётся; квоты не перераспределяются. Вопрос должен иметь правильный ответ в `right_answer`. Частота — число записей пары `test_id`, `question_id`; сначала берутся неиспользованные/редкие, равенство — случайно. Вопросы общих тем не дублируются. Порядок показа перемешивается и сохраняется порядком вставки вопросов попытки.

При ответе сохраняется только JSON в `active_test_answer` и признак `is_answered` в `active_test_question`. Проверяются формат ответа и принадлежность вариантов вопросу, но не правильность. Пропуск хранится как JSON `null`. Повторные запросы с прежним `question_id` не отвечают на следующий вопрос. Интерфейс отсчитывает 60 секунд для каждого вопроса.

Только `finish` проверяет ответы и рассчитывает баллы по текущим `right_answer` и `question_type`. Выбор проверяется как множество, порядок — как последовательность, ввод — без внешних пробелов и без учёта регистра. Правильный ответ получает `success_score`, ошибка или пропуск — `failure_score`. Полный балл, положительный или отрицательный, записывается в `user_topic_stat` для каждой связанной через `question_topic` темы, включая темы вне категорий настройки теста. Один ответ может создать несколько записей статистики, но только одну запись частоты.

Снимок `completed_test`, статистика, частота и статус `passed` сохраняются одной транзакцией. В снимке — одна запись на вопрос, значения вместо ID, пропуск — `null`; названия всех связанных тем и категорий перечисляются через запятую в строковых полях `topic` и `category`. Отмена удаляет ответы и вопросы попытки, оставляя `active_test` со статусом `rejected`; снимок, статистика и частоты не создаются. Все изменения одной попытки сериализуются блокировкой её `test`; повторное завершение не начисляет результаты снова. Дополнительные поля в `active_test_question` не нужны.

Проверки без рабочей БД: `php tests/test-attempts.php`, `php tests/attempt-api.php`. Интерфейс NLUser: `test/test_attempt_test.dart` и `test/test_panel_test.dart`.

Модуль user во внешнем Yii-проекте. Авторизация реализована, CRUD-операции остаются заглушками HTTP 501.

## Авторизация

- POST /user/auth/login — вход по username или email и password; доступен без токена.
- GET /user/auth/me — id и username текущего пользователя.
- POST /user/auth/logout — отзыв токена, ответ {"success":true}.

Вход принимает JSON, например {"username":"login","password":"password"} или {"email":"user@example.com","password":"password"}.
Ответ содержит auth_key, token_type: Bearer и user (id, username). В базе сохраняется только SHA-256 хеш токена.
Новый вход заменяет прежний токен. Автоматического срока истечения пока нет. За пределами локальной разработки используйте HTTPS.
400 — неверный формат данных, 401 — неверные реквизиты или токен. Cookies и CSRF-токен для входа не требуются.
Проверки авторизации на SQLite в памяти: php tests/user-auth.php.

Защищенные маршруты уже проверяют Authorization: Bearer <auth_key> через существующую модель User.
Без действующего токена — 401. Хранилище учетных записей и auth_key общее с admin API:
вход через любой модуль заменяет прежний токен этой учетной записи. Cookies не заменяют Bearer-токен.
Операции прохождения проверяют владельца теста и действующий доступ к курсу.

## CRUD-маршруты

Для каждого ресурса доступны:
GET /user/{resource} — список;
GET /user/{resource}/{id} — одна запись;
POST /user/{resource} — создание;
PUT или PATCH /user/{resource}/{id} — редактирование;
DELETE /user/{resource}/{id} — удаление.

Ресурсы: courses, categories, tests, active-tests, topics, questions, question-types.

Списки по родителю:
- GET /user/courses/{course_id}/categories
- GET /user/categories/{category_id}/topics
- GET /user/topics/{topic_id}/questions

На общих списках categories, topics и questions планируются соответственно query-параметры course_id, category_id и topic_id.
tests использует владельца из токена; active-tests предоставляет операции прохождения текущего пользователя, описанные ниже.

OPTIONS поддерживается для CORS. Разрешенные источники задаются в modules.user.corsOrigins.
Маршруты требуют настройки веб-сервера на web/index.php. Прямые Yii-маршруты user/course/index и аналогичные также доступны.

Проверка маршрутов без базы: php tests/user-api-routes.php.

## Пользовательские тесты

### Обработчики типов вопросов

`question_type.code` содержит стабильный ключ обработчика из `services/question/QuestionHandlerRegistry`: `choice_4_single`, `choice_multiple`, `input_text`, `ordering`. Ключ не зависит от названия и идентификатора типа. `QuestionType` проверяет регистрацию обработчика и соответствие `category`; неизвестный или несовместимый обработчик блокирует создание попытки.

- `choice_4_single`: один правильный вариант и три случайных неправильных из банка, затем перемешивание. Требуется ровно один правильный вариант и минимум три неправильных; выбирать можно только один ответ.
- `choice_multiple`: все варианты банка в случайном порядке; допускается выбор нескольких, правильность определяется точным совпадением набора с одним из допустимых ответов.
- `input_text`: варианты не выдаются, ввод сравнивается без учёта регистра и крайних пробелов.
- `ordering`: все варианты перемешиваются, пользователь должен восстановить одну из допустимых полных последовательностей.

Перед выдачей вопроса обработчик формирует варианты. Сервер в одной транзакции помечает `active_test_question.is_shown = 1` и создаёт единственную запись `active_test_answer` с `answer = NULL` и `presented_options` (идентификаторы, тексты и порядок вариантов). При ответе обновляется эта запись; принимаются только показанные варианты. Правильные ответы клиенту не выдаются. Текст вопроса, код типа, баллы и правильные ответы читаются из банка, полного снимка вопроса нет.

Повторный `start` существующей попытки и `resume` выдают следующий вопрос с `is_shown = 0`: прежний показанный вопрос остаётся с ответом NULL. Закрытие страницы не требует отдельного запроса. Пропуск и таймаут также оставляют NULL и выдают следующий вопрос. После последнего показанного вопроса возвращается `question = null`, можно завершить тест. Запоздавший ответ на предыдущий вопрос не изменяет его и не пропускает текущий. При завершении в `completed_test` копируются тексты и порядок именно показанных вариантов из `active_test_answer`, ответ пользователя и результат.

Поля включены в миграции создания таблиц: `question_type.code`, `active_test_question.is_shown` и `active_test_answer.presented_options`; `active_test_answer.answer` допускает SQL NULL. Поля `presentation` и `is_answered` отсутствуют. Код типа заполняет владелец данных. Допустимые коды: `choice_4_single`, `choice_multiple`, `input_text`, `ordering`. Для нового поведения добавьте реализацию `QuestionHandler` и зарегистрируйте код в реестре. Уже применённые миграции создания повторно не выполняются; актуализацию существующей схемы выполняет владелец проекта.

Проверки без рабочей БД: `php tests/question-handlers.php`, `php tests/active-test-handlers.php`, `php tests/question-handler-schema.php`, `php tests/question-type-category.php`. Последняя проверяет модель на SQLite, проверка схемы — создание и откат MySQL DDL без подключения к серверу.

- `GET /user/tests` — тесты владельца токена из зарегистрированных баз курсов: `items` с `id`, `course_id`, `name`, `question_count`, `materials` (курс: `course_id`, `course_name`, список названий `categories`). Идентификатор теста локален для базы; полная идентичность — пара `course_id` и `id`. Категории читаются из `category` той же базы. Каталог и проверка подписки остаются в основной БД.
- `GET /user/tests/materials` — дерево активированных курсов действующей подписки и их категорий: `items`, у курса `id`, `name`, `categories` с `id`, `name`.
- `POST /user/tests` — JSON `{"name":"Мой тест","question_count":10,"materials":[{"course_id":1,"category_id":2}]}`. Создаёт тест и связи одной транзакцией в базе выбранного курса, возвращает 201 с `id`, `course_id`, `name`, `question_count`. Все категории должны принадлежать одному курсу; смешанный выбор возвращает 400. Пользователь берётся из токена; название обязательно (до 255 символов), question_count — обязательное целое число от 1 до 30, нужна хотя бы одна доступная категория. Повторные категории объединяются. Доступ проверяется заново при сохранении.

Категории читаются из таблиц курса по проверенному alias. Идентификатор категории уникален только внутри курса, поэтому связь содержит и `course_id`. Сохранённый материал виден в списке даже после окончания подписки. Прохождение создаёт попытки в БД курса; незавершённая попытка отображается кнопкой «Продолжить».

Итоговая структура связи включена в миграцию создания `m260913_000008_create_test_category_table`; актуализацию существующей базы выполняет владелец проекта. Проверка без рабочей БД: `php tests/user-tests.php` (SQLite в памяти).

## API подписки и платежей

Все операции требуют Bearer-токен, пользователь определяется только из него.

- `GET /user/subscription` — `subscription` (тариф, начало и конец, либо `null`) и `slots` (`total`, `used`, `available`). `/user/subscriptions` — алиас этой сводки.
- `GET /user/tariffs` — персональные предложения: `items` с `id`, `name`, `price`, `duration_days`, `course_limit`, `is_switch`, `remaining_value`, `credit_amount`, `payment_amount`. Цена `price` — полная стоимость тарифа, `payment_amount` — сумма к оплате с учётом остатка текущей подписки.
- `GET /user/payments?page=1` — история платежей: `items` и `pagination`, по 10 строк, `payed_at DESC, id DESC`. Поля строки: `id`, `tariff_name`, `course_limit`, `duration_days`, `payed_at`, `payment_amount`, `discount_type`, `discount_value`. Суммы — десятичные строки; тип скидки — `percent` / `amount`. Данные тарифа и скидки читаются из связанных таблиц; сумма берётся из самого платежа.
- `POST /user/payments` — тестовая оплата, JSON: `{"tariff_id":1,"expected_amount":"700.00","discount_code":"OPTIONAL"}`. Ответ: `payment_id` и сводка подписки. Цена и скидка рассчитываются сервером. Необязательный `expected_amount` — показанная пользователю сумма, а не источник цены. При несовпадении с новым расчётом сервер возвращает 409 без записи платежа. Платёжный провайдер и защита от повторной обработки пока не подключены. Каждый успешный запрос записывает отдельный платёж.
- `POST /user/courses/{id}/activate` — занять слот текущей подписки. Ответ: `slot_id`, `expires_at` (дата окончания связанной подписки, в слоте не хранится). Повтор для активного курса не расходует второй слот.

Каждая оплата обновляет одну и ту же подписку пользователя: тариф, лимит, начало и конец срока. Подписка не ссылается на платёж; история платежей ведётся отдельно. Если новый лимит меньше числа активных курсов, лишние слоты деактивируются начиная с последних активаций (`activated_at DESC, id DESC`). Дата активации сохраняется, дата отключения записывается в `deactivated_at`. Увеличение лимита не восстанавливает отключённые курсы: нужна явная активация, создающая новую запись слота.

Отсутствие действующей подписки или свободных слотов при активации даёт 409, неверный промокод — 400, неизвестный тариф/курс — 404. По истечении срока подписки доступ исчезает автоматически. При последующей оплате старые слоты закрываются, не включаясь заново. До первой оплаты сводка пуста.

Проверка бизнес-сценариев, аутентификации и владельца без рабочей БД: `php tests/user-subscriptions.php`.

Для Apache с CGI/FastCGI в `web/.htaccess` включён `CGIPassAuth On`: он передаёт заголовок Authorization в PHP. Без него вход по паролю работает, но `/user/auth/me` и `/user/auth/logout` получают запрос без токена и возвращают 401.

Проверка через работающий Open Server: `php tests/user-auth-http.php --local-apache`. Она использует `http://nl.local` и БД из `config/db/db.php`, создаёт временную учётную запись и удаляет её в `finally`. Проверяются CORS, вход, три независимых восстановления сессии, выход, удаление токена в БД и отказ для отозванного токена. Существующие учётные записи не изменяются.

## Перерасчёт при смене тарифа

Остаточная стоимость = цена текущего тарифа × оставшиеся дни / полный срок подписки. Дни считаются как 24-часовые интервалы, неполный оставшийся день округляется вверх; результат округляется до копеек. Источники срока — `starts_at` и `expires_at`. Если остаток строго больше 100 ₽, он вычитается из стоимости нового тарифа. Итог не ниже нуля. При остатке ровно 100 ₽ или меньше зачёта нет. Истёкшая/будущая подписка не даёт зачёт; повторная оплата того же тарифа также не является переходом.

При промокоде сначала рассчитывается скидка от полной цены нового тарифа, затем вычитается остаток подписки. В `payment_amount` записывается итог, включая ноль при бесплатном переходе. Лимиты и деактивация последних курсов работают как при обычной оплате. Расчёт выполняется заново внутри транзакции оплаты.
